Your Agentic Workforce Needs a Circuit Breaker

One background coding agent consumed 46.55 million fresh input tokens without another human prompt. The lesson is larger than one agent, one harness or one cache anomaly.

24 August 2026·By 48Nauts·8 minute read

We are building toward an agentic workforce: tens, hundreds and eventually thousands of automated workers operating tools, writing code, conducting research and delegating tasks. Most of the conversation is about making those agents more capable and more autonomous.

Far less attention goes to the operational question: what happens when just one of them fails to stop?

That happened in our own environment. A background coding agent continued working for nearly four hours. It made 320 model calls and consumed 46.55 million fresh input tokens. After the initial instruction, there was no new human prompt on any of those calls.

By rogue, I do not mean conscious, malicious or rebellious. I mean an automated worker operating outside its expected behavioral or resource boundaries.

It looked like legitimate work

The agent did not break into anything. It used an authorized session, an approved model and the tools it had been given. Individual requests looked like ordinary agent activity. The failure only became obvious when we looked at the sequence as a whole.

The session began immediately after a request to implement four features. It then continued alongside the visible conversation. Of its 320 calls, 244 produced another tool call. Its recorded history grew from 19 messages to 662, while fresh input eventually reached 273,886 tokens per call.

That distinction matters. A resource incident in an agentic workforce may not look like an intrusion. It may look like a worker being productive.

A small project can still create a large incident

The website being changed was small. The repository size was not the problem. Model consumption is driven by what the harness sends on every request, not by the number of files in a project.

As the agent worked, its conversation and tool history expanded. That growing prefix was repeatedly sent to the model. We observed no corresponding cache reads, so previously seen context appeared as fresh input again. Each turn therefore carried more history than the last, and the cost of continuing increased as the loop progressed.

Our evidence establishes the traffic pattern: expanding history, absent cache reads, repeated tool calls and no new human instruction. It does not expose the harness's private internal reasoning, so we should not pretend it proves a single hidden trigger. The behavior is consistent with a resumed background session that kept advancing its tool loop while failing to benefit from prompt-cache reuse.

The blast radius is shared capacity

API incidents are easy to imagine because they arrive as a bill. Subscription plans create a different risk. A request may have zero metered API cost and still consume scarce five-hour or weekly capacity.

In this case, one session reached the five-hour limit and contributed to a second limit event, while the available weekly Max allowance fell dramatically. One automated worker consumed capacity that every other worker—and the human operator—depended on.

Now scale that operating model from a handful of agents to hundreds. Without identity, attribution and resource isolation, one runaway worker can degrade the entire workforce. A shared subscription becomes the equivalent of a production cluster with no per-process limits.

Observability is necessary, but it is not containment

NautGate let us reconstruct what happened because the requests crossed a common gateway. We could identify the source application, session, timing, call count, token growth, cache behavior and concurrency with other work.

If you do not have NautGate—or an equivalent evidence layer—how would you find this out? A capacity limit tells you that something consumed the allowance. It does not tell you which agent did it, what application launched it, whether its context kept growing, whether its cache stopped working or why it failed to stop.

But the investigation also exposed a gap: seeing an incident after it happens is not the same as stopping it while it happens. The gateway had evidence, yet it did not have a capacity-aware circuit breaker for subscription traffic.

That became the design brief for Max Guard.

What a circuit breaker must know

A useful guardrail cannot rely on cost alone. It needs to understand the unit of work and the behavior around it:

  • Identity: which agent or API key is acting?
  • Attribution: which application, project, run and session launched it?
  • Capacity: how much fresh input has it consumed in the current rolling window?
  • Cache integrity: is a stable prefix being sent repeatedly without cache reuse?
  • Behavior: is the session producing an unusual tool-call streak or growing without human input?
  • Containment: can this session be paused without taking down every other agent?
  • Evidence: can an operator explain why the intervention occurred and safely resume work?

NautGate v0.5.0 now tracks fresh input, cache reads and writes, output, requests and rolling five-hour and weekly pressure. Policies can observe, warn or pause. A paused Max request receives a non-retryable response and does not silently fall through to metered Anthropic credits.

Autonomy requires boundaries

Organizations already understand this principle for human and machine workforces. Employees have identities and spending authority. Processes have memory and CPU limits. Cloud accounts have budgets, quotas and alerts. Production systems have circuit breakers.

Agents need the same operational discipline. Not because they are plotting against us, but because software fails, integrations drift, caches disappear, retries compound and an apparently reasonable loop can continue much longer than intended.

The most dangerous agent may not be one that refuses its instructions. It may be one that follows them indefinitely.

An agentic workforce should not depend on every model call, harness decision and cache layer behaving perfectly. It should assume that one worker will eventually go outside its expected boundary—and make that event visible, attributable and containable.

Capability creates the workforce. Guardrails make it operable.
